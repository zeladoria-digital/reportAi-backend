SPRINT 01 -------------------------------------------------------------------------------------------------------------------------------------------------------------

(Sessão e Segurança):
Foco: Login e Autorização (Firebase Auth).
Tarefas: Configurar os provedores de login (E-mail/Senha e Google). Criar as Security Rules iniciais no Firestore garantindo que apenas usuários logados possam escrever no banco, e que cidadãos só vejam seus próprios dados.
Tarefas associadas: RF01, RF22, RNF06, RNF07.

RF01: O sistema deve permitir que o cidadão realize cadastro e login (autenticação simplificada, ex: via Google/Firebase Auth).
RF22: O sistema web deve possuir autenticação restrita para gestores públicos.
RF06: O aplicativo deve possuir funcionamento offline-first, permitindo que o cidadão registre a ocorrência mesmo sem internet, salvando a foto e as coordenadas localmente para sincronização automática em background (segundo plano) quando houver rede Wi-Fi ou dados móveis.
RF07: O sistema mobile deve extrair os metadados da foto (dados EXIF) no momento do clique, validando se a data de criação do arquivo bate com a data do envio, para evitar que o cidadão faça upload de fotos antigas baixadas da internet.


SITUAÇÃO ATUAL:

Implementado:
Provedores de login (E-mail/Senha) — ativado no Firebase Authentication e integrado ao backend com auth.verifyIdToken()
Security Rules do Firestore — configuradas e testadas, garantindo que usuários não autenticados não acessam os dados e cidadãos só veem os próprios dados
RF01 — Cadastro e login — endpoint POST /users/register cria o usuário no Firebase Auth e no Firestore, e POST /users/login autentica via idToken do Firebase
RF22 — Autenticação restrita para gestores — endpoint POST /users/login-dashboard verifica se o usuário tem papel de gestor/admin antes de permitir acesso

Parcialmente implementado:

RNF07 — Validação EXIF — a lógica foi implementada no complaintModel.js mas ainda não foi testada pois depende do frontend mobile enviar os metadados

Não implementado:
Provedor Google — a rota POST /users/auth/google não foi criada e nem testada
RNF06 — Offline-first — é responsabilidade exclusiva do frontend mobile, não do backend. Precisa ser implementado no React Native com AsyncStorage ou similar para salvar as ocorrências localmente e sincronizar quando houver conexão


SPRINT 02 -------------------------------------------------------------------------------------------------------------------------------------------------------------

(Integração IoT e Storage):
Foco: Recepção de anomalias e fotos.
Tarefas: Configurar as regras do Firebase Storage para receber o upload das fotos do cidadão. Criar regras para aceitar requisições (POST) diretas do hardware IoT contendo JSON (Coordenadas + Categoria + Foto).
Tarefas associadas: RF16, RF17.
(Monitoramento de Frota):
Foco: Status do hardware.
Tarefas: Criar a coleção e as regras para receber os "Heartbeats" da frota a cada 5 minutos.
Tarefas associadas: RF19.

RF16: O dispositivo deve enviar apenas a foto da anomalia, o GPS e a categoria do problema para a nuvem (Firebase), descartando o restante do vídeo para economizar dados.
RF17: O dispositivo embarcado deve possuir um buffer local (armazenamento temporário, como um cartão SD). Se o caminhão passar por uma área de "sombra" (sem sinal 3G/4G), o sistema deve salvar as detecções da IA localmente.
RF19: O dispositivo de hardware deve enviar um "heartbeat" (sinal de vida ou ping) para o servidor a cada 5 minutos, informando as coordenadas atuais do caminhão para que o gestor saiba onde a frota está em tempo real, mesmo que nenhum buraco tenha sido detectado.

SITUAÇÃO ATUAL:
Implementado:

Regras do Firestore — configuradas e testadas
Rota para receber dados do IoT — POST /complaints/iot
Model de complaints unificado com source (citizen/iot)
Coleção iot_devices com registro e heartbeat
Heartbeat — POST /iot/devices/:id/heartbeat a cada 5 minutos (RF19)
Testes das rotas de Device iot e vehicle no Postman

Parcialmente implementado:

RF16 — a rota recebe photoUrl mas o upload para o Storage está pendente pelo plano Blaze
RF17 — buffer offline discutido mas não implementado — é responsabilidade do hardware/firmware, não do backend
